# Code Review Harness

## 적용 시점과 권한

- 변경 작업 완료 전 Self Review와 Diff Review 필수
- PR Review는 사용자 요청 시에만 수행
- 리뷰만 요청받으면 읽기·진단·보고만 수행하고 코드 수정, Commit, Push와 PR 댓글 게시 금지
- 구현 중 발견한 문제는 요청 범위 내 최소 수정, 승인 대상은 `.ai/RULES.md` 준수
- 자동 검증과 사람 관점의 리뷰는 별도 절차이며, Script 성공을 리뷰 완료로 간주하지 않음

## 범위와 Context

작업 시작 상태와 이번 변경을 구분한다. Diff → 변경 Symbol → 호출부 → 관련 설정·Test 순서로 필요한 범위만 읽는다. 기존 사용자 변경은 검토 경계를 명시하고 임의로 되돌리지 않는다.

- 공통: 이 문서
- Backend 변경: `backend-review.md`의 해당 절
- Frontend 변경: `frontend.md`의 해당 절
- DB 변경: `../architecture/DATABASE_SCHEMA.md`

문서만 변경한 작업은 문서 정합성·참조·범위·노출 위험을 검토한다. 무관한 코드 체크리스트는 `NOT APPLICABLE`이다. 별도 Agent나 전체 Repository 재검토를 매번 강제하지 않는다.

## Self Review

관련 자동 검증 후 다음을 확인한다. 실행 불가 검증이 있어도 리뷰는 수행하되 전체 완료로 표시하지 않는다.

- Correctness: 확정된 요구사항, 정상·실패·경계 조건
- Consistency: 실제 구현 Pattern과 계약 일치
- Scope: 최소 변경과 기존 사용자 작업 보존
- Simplicity·Maintainability: 불필요한 추상화, 중복 책임과 복잡성
- Performance: 변경 경로에서 입증 가능한 비용·지연 문제
- Security: 인증·인가, 입력 검증, Secret과 개인정보 노출
- Error Handling: 실패 은폐, 내부 원인 노출과 복구 경로
- Testability: 바뀐 동작과 중요한 실패 경로의 검증

## Diff Review

Unstaged·Staged Diff와 비무시 신규 파일을 모두 확인한다. `git diff --check`는 공백 검사일 뿐 의미 검토를 대체하지 않는다.

- 관계없는 파일, Naming 변경과 Formatting Noise
- Debug·Temporary 코드와 이번 변경으로 생긴 미사용 코드
- 불필요한 Dependency와 설정 변경
- 의도하지 않은 Public API·Security·Schema 계약 변경
- Secret, 실제 환경값과 추적 금지 파일
- Test 삭제·Skip·Assertion 약화
- 함께 바뀌어야 할 Test·설정·문서 누락

## 근거와 심각도

지적에는 파일·줄, 발생 조건, 실제 영향, 코드 또는 Test 근거, 최소 수정 방향과 검증 방법을 포함한다. 취향이나 막연한 가능성을 결함으로 단정하지 않고 지적 수를 채우지 않는다.

- 결함: 근거와 발생 조건이 확인된 문제
- 확인 필요: `[판단에 필요한 구체적인 정보가 필요합니다.]` 형식으로 사용자에게 요청
- 선택적 제안: 비필수 가독성·유지보수 개선
- 기존 문제: 이번 변경 이전부터 존재한 문제로 분리 보고

| 등급 | 기준 | 완료 처리 |
| --- | --- | --- |
| P0 | 중대한 보안 침해·광범위한 데이터 손실 등 긴급 문제 | 완료 차단 |
| P1 | 핵심 기능 실패·중대한 회귀 | 완료 차단 |
| P2 | 특정 조건의 기능 오류·의미 있는 계약 위반 | 수정 또는 사용자 명시적 보류 |
| P3 | 비필수 개선 제안 | 완료 차단하지 않음 |

보류된 결함을 `PASS`로 바꾸지 않는다. P2 보류 승인은 해당 지적에만 적용하며 필수 검증의 FAIL·NOT RUN을 면제하지 않는다. 핵심 요구사항 판단이 불가능한 확인 사항도 완료 전에 해소한다.

## 수정 Loop

자동 검증 → Self Review → 발견 문제의 근거 확인 → 최소 수정 → 같은 검증 → 영향 범위 재리뷰 → 전체 Diff Review → 완료 조건 평가

Diff 문제도 수정·검증·재리뷰로 되돌린다. 같은 실패가 세 번 반복되면 추측성 수정을 중단하고 사실·시도·결과·원인 후보·필요한 정보를 보고한다.

## 요청 시 PR Review

PR 링크 또는 비교 기준을 확인하고 기준 Commit과 검토한 Head Commit을 기록한다. 기준을 알 수 없으면 `[PR 리뷰에 사용할 PR 링크 또는 기준 브랜치 정보가 필요합니다.]`라고 요청한다.

- PR 목적과 전체 변경의 일치, Commit 사이의 누락
- CI 결과와 로컬 검증의 차이
- API·Schema 호환성, 배포 순서와 Rollback 조건
- 관련 없는 변경 혼입
- 검토 후 새 Commit이 추가되면 기존 결론을 자동 승계하지 않음

## 완료 보고

검토 범위, 자동 검증, Self Review, Diff Review를 `PASS / FAIL / NOT RUN / NOT APPLICABLE`로 기록한다. 발견·해결한 문제, 미해결·보류 항목과 승인 근거, 검증하지 못한 위험을 간결하게 남긴다.

문제를 찾지 못했으면 “검토 범위에서 수정이 필요한 문제를 발견하지 못함”으로 보고하고 무결함을 보장하지 않는다. 상세 항목을 매번 반복 출력하지 않고 지적과 미검증 경계 중심으로 보고한다.
